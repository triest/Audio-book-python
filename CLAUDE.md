# audiobook — заметки для Claude

Инструмент для превращения FB2-книг в аудиокниги на русском. GUI на Tkinter
(`fb2_reader_gui.py`) + движок конвертации (`fb2_reader.py`) + несколько TTS-движков,
часть из которых — локальные REST-сервисы на голом Windows (без Docker).
Работает на машине пользователя (RTX 4060 Ti 16GB), сессия обычно подключается
через remote-devices bridge, а не напрямую.

**Рабочая копия — только `J:\audiobook`.** Папка на диске C (`C:\Users\user\audiobook`)
из работы исключена (проект перенесён на J: в сентябре 2026); не читать, не
писать и не упоминать её как актуальную — если где-то на диске ещё остались
файлы по старому пути, это неактуальные остатки переноса, не рабочая копия.
GitHub-зеркало: https://github.com/triest/Audio-book-python .

## ТЗ (техническое задание)

Цель проекта: по FB2-файлу книги на русском языке получить готовую аудиокнигу
(.wav/.mp3, по главам), с минимальным ручным трудом пользователя и максимально
естественным звучанием.

Обязательные свойства:

- **Разбиение по главам** — FB2 парсится на главы/фрагменты, каждая глава
  озвучивается и собирается в отдельный аудиофайл.
- **Несколько взаимозаменяемых TTS-движков** — облачные (Yandex SpeechKit,
  Qwen3-TTS/DashScope, Google TTS через `online`) и локальные (Silero
  локально/REST, Piper, CosyVoice/ESpeech RL-V2/XTTS-v2, CosyVoice3, Qwen3-TTS
  через Pinokio) — пользователь выбирает режим в GUI под конкретную книгу/задачу
  (качество vs. скорость vs. стоимость).
- **Корректные ударения в русском тексте** — многослойная система (словари
  конкретных слов книги → автоматический модуль расстановки ударений →
  встроенное угадывание TTS-движка), т.к. большинство движков без этого дают
  заметно неестественную речь на многосложных/редких словах и омографах.
- **Атрибуция говорящих и эмоциональная окраска** (там, где это применимо) —
  опциональные LLM-режимы поверх базовой озвучки: кто говорит реплику
  (`attribute_speakers_llm`) и с какой интонацией/эмоцией читать абзац
  (`classify_paragraph_emotions_llm`), не ломающие базовый режим при отказе LLM.
- **Голосовые профили и клонирование голоса** — там, где движок это
  поддерживает (CosyVoice/CosyVoice3), пользователь может подключить свой
  образец голоса.
- **Работа на голом Windows пользователя, без Docker** — окончательное решение,
  все движки — обычные Windows-подпроцессы в своих `venv`, `install.bat`
  разворачивает всё окружение с нуля.
- **Пост-обработка** (`audio_cleanup.py`) — нормализация громкости по кускам и
  обрезка аномальных пауз в уже готовых файлах, опционально, не трогает
  исходники по умолчанию.

Нефункциональные требования: минимум ручной настройки на новую книгу (профили
голосов/атрибуции переиспользуются), устойчивость к сбоям отдельного движка
(деградация до более простого пути, а не падение всей главы — см. Yandex
smart-emotion), воспроизводимость через `install.bat` на новой машине.

## Куда движемся (направление развития)

- Дальнейшее наращивание числа TTS-движков и выбор лучшего по звучанию для
  русского (тестируется прежде всего на слух пользователем на его машине;
  ESpeech RL-V2 на данный момент — эталон качества для этого проекта).
- Более тонкое управление интонацией/эмоцией текста через LLM-разметку
  (`--smart-emotion`, пока Silero REST — приоритетный путь, Yandex — второй,
  менее приоритетный) — по возможности распространять этот же принцип и на
  другие движки, где это технически осмысленно (SSML-подобный контроль
  просодии или явный emotion-параметр API).
- Постоянный мониторинг новых открытых и облачных TTS-движков и модулей
  качества речи (ударения, просодия) — см. следующий раздел про ежемесячный
  поиск.
- Упрощение установки и обновления окружения для пользователя — единая точка
  входа `install.bat`, без ручных `pip install` в обход неё (см. «Жёсткие
  правила»).

## Поиск новых движков и установка обновлений

- Раз в месяц работает автоматическое scheduled-задание (создано через
  `mcp__claude-code-remote__create_trigger`, id `trig_012un2UHqM79V94jpihQF9fB`),
  которое ищет новости о новых/обновлённых TTS-движках, релизах существующих
  движков (Silero, CosyVoice/CosyVoice3, Piper, Qwen3-TTS, silero-stress и
  т.п.) и о качестве синтеза/ударений для русского языка, и присылает
  пользователю краткую сводку. Отдельно от этого пользователь сам иногда
  присылает ссылки на статьи/релизы (Habr, GitHub) — их тоже нужно оценивать
  по этому же принципу.
- Порядок оценки нового движка/фичи перед интеграцией:
  1. Проверить, есть ли у движка локальный REST/Gradio-интерфейс или готовый
     Python-пакет (аналогично Qwen3-TTS/CosyVoice) — без этого интеграция
     осмысленна только как ручной внешний шаг, не как режим GUI.
  2. Для ОБЛАЧНОГО сервиса — **прежде чем писать код**, явно проверить страницу
     регистрации/подключения на предмет "недоступно для новых клиентов" —
     урок SaluteSpeech (см. «Рассмотренные и отложенные TTS-движки»): сама
     документация API может выглядеть актуальной и не иметь предупреждений
     об этом на странице обзора.
  3. Проверить пригодность именно для АУДИОКНИГ (длинные тексты), а не только
     для коротких фраз/голосовых ассистентов — пример: OmniVoice сильна на
     коротких фразах, но автор статьи сам не рекомендует её для длинных
     текстов из-за артефактов.
  4. Спросить пользователя, добавлять ли новый движок КАК ОТДЕЛЬНЫЙ режим в
     GUI или предложить выбор (движок vs. движок) внутри существующего режима
     — см. прецедент со stress_engine (выбор через интерфейс, не жёсткая
     замена).
  5. Новую зависимость — только строкой в `install.bat` (см. ниже), не
     советовать пользователю ставить её вручную.
  6. Если движок в итоге не подошёл/отложен — не удалять исследование молча,
     а зафиксировать в разделе «Рассмотренные и отложенные TTS-движки» ниже:
     что за движок, почему отложен, что нужно перепроверить, если пользователь
     попросит вернуться к нему.
- Установка/обновление зависимостей для пользователя — всегда только через
  `install.bat` (запускается пользователем на его Windows-машине; сессия
  Claude не выполняет `.exe`/venv-код напрямую через remote-devices bridge —
  см. «Отладка через remote-devices bridge»). Если версия пакета в `install.bat`
  устарела и есть новый релиз, полезный для проекта — обновить версию/строку
  установки там же, а не советовать ручной апгрейд.

## Структура

- `fb2_reader_gui.py` — GUI (Tkinter), ~184К, все вкладки/режимы озвучки, автозапуск
  локальных REST-сервисов, управление голосовыми профилями.
- `fb2_reader.py` — логика чтения FB2, разбиения на главы/фрагменты, вызовы TTS,
  сборка готовых .wav/.mp3.
- `cosyvoice_rest_service.py` — REST-сервис для F5-TTS / ESpeech RL-V2 / XTTS-v2,
  порт 5011, окружение `.venv_cosyvoice`.
- `cosyvoice3_rest_service.py` — REST-сервис для CosyVoice3 (Fun-CosyVoice3-0.5B),
  порт 5012, **отдельное** окружение `.venv_cosyvoice3` (несовместимые версии
  зависимостей, torch==2.3.1 и т.д.) и отдельный клон репозитория `CosyVoice3/`
  (`FunAudioLLM/CosyVoice`, install.bat делает `git clone`).
- `silero_rest_service.py` — REST-сервис Silero.
- `install.bat` — ставит все окружения и качает веса моделей.
- `audio_cleanup.py` — отдельный скрипт (запускается вручную, вне GUI), не
  синтез, а пост-обработка уже ГОТОВЫХ .wav/.mp3: локальная (по кускам,
  не по общему пику файла) нормализация громкости + обрезка аномально
  длинных пауз до канонической длины. Не трогает исходники по умолчанию
  (пишет с суффиксом `_clean`, `--in-place` — явный флаг для перезаписи).
  Зависимость (pydub) уже в основном наборе `install.bat`.
- Режимы озвучки в GUI: `online` (Google TTS), `silero`/`silero_rest`, `offline`
  (локальные голоса), `yandex` (Yandex SpeechKit), `cosyvoice` (единый режим —
  URL REST-сервиса определяет F5/ESpeech/XTTS на 5011 или CosyVoice3 на 5012),
  `piper`, `qwen_tts`/`qwen_tts_local` (облачный DashScope и локальный через
  Pinokio).

## Умная эмоция Silero REST (--smart-emotion) и Yandex SpeechKit (--yandex-smart-emotion)

Основной вариант — **Silero REST** (`run_silero_rest`, флаг `smart_emotion`):
у Silero нет отдельного API-параметра эмоции (в отличие от Yandex), поэтому
эмоция каждого абзаца, определённая `classify_paragraph_emotions_llm` (набор
меток `SILERO_EMOTION_PROSODY`: neutral/joy/sadness/fear/anger/calm, каждая
сопоставлена с rate/pitch), выражается через SSML `<prosody rate=".."
pitch="..">`, которым оборачивается `<p>` абзаца в `text_to_ssml`
(параметр `paragraph_prosody` — список ПО ПОЗИЦИИ абзаца, не по тексту,
т.к. текст абзаца меняется после расстановки ударений). Классификация — один
LLM-запрос на ГЛАВУ (`_chapter_para_prosody`, строится в основном цикле
`run_silero_rest` до чанкинга на `max_len`), не на каждый чанк.

Yandex SpeechKit (`run_yandex`, флаг `smart_emotion`) — более ранний и
более ограниченный вариант того же принципа: там используется штатный
параметр запроса `emotion`, а не SSML, поэтому набор эмоций жёстко
ограничен вокабуляром самого Yandex (`YANDEX_EMOTION_VOICES`: good/neutral,
и evil только у `jane`) и только для голосов `ermil`/`jane`. Оставлен в
коде как рабочая, но менее приоритетная опция — если пользователь явно не
попросит её убрать, трогать не нужно.

Вместо ЕДИНОЙ `emotion` на всю озвучку (Yandex поддерживает эмоции только у
голосов `ermil`/`jane` — см. `YANDEX_EMOTION_VOICES`), LLM (тот же
провайдер/ключ, что и атрибуция говорящих — `attribute_speakers_llm`,
но НЕ требует включённой галочки атрибуции, см. `emotion_attribution` в
`run_yandex`) определяет эмоцию каждого абзаца по смыслу текста —
`classify_paragraph_emotions_llm` (диспетчер, аналогичный по структуре
`attribute_speakers_llm`, но текстовый JSON-ответ вместо tool_use — тройка
`classify_paragraph_emotions_{anthropic,gemini,yandexgpt}`).

Технически: `run_yandex` при `smart_emotion=True` и хотя бы одном
используемом голосе из `YANDEX_EMOTION_VOICES` уходит с обычного пути
(`_chunk_voice_groups`, пакует несколько абзацев в один запрос до
`YANDEX_MAX_CHARS`) на отдельный путь синтеза ПО АБЗАЦАМ — каждый абзац
синтезируется отдельным запросом со своей emotion (иначе на нескольких
абзацах в одном запросе была бы одна emotion на всех). При ошибке LLM —
откат на единую `emotion`, не срывая главу.

## Жёсткие правила (не нарушать без явного запроса пользователя)

- **Никакого Docker.** Пользователь явно и окончательно отказался от Docker для
  CosyVoice3 (`docker/cosyvoice3/` — исторический артефакт, не развивается) —
  все движки запускаются как обычные Windows-подпроцессы в своих venv.
- **ESpeech RL-V2 (движок на порту 5011, режим `cosyvoice`) — подтверждённо
  хорошо работает для русского.** Не трогать её логику синтеза без явного запроса.
- Не коммитить `fb2_reader_settings.json` (там ключи Yandex/Anthropic) и
  `dialogue_characters.json` — уже в `.gitignore`.
- **Все зависимости/пакеты ставятся ТОЛЬКО через `install.bat`.** Никогда
  не предлагать пользователю ручной `pip install ...` в обход него, даже
  как "альтернативный вариант" — новую зависимость нужно дописать в
  соответствующий venv-блок `install.bat` (см. существующие примеры вроде
  `ruaccent`/`silero-stress`), а не советовать поставить её вручную.

## Конвенция доставки правок сервисов (обязательна)

Каждый REST-сервис несёт `SERVICE_VERSION` (в `*_rest_service.py`) и GUI сверяет
её с `..._EXPECTED_SERVICE_VERSION` (в `fb2_reader_gui.py`) при принятии решения,
перезапускать ли уже работающий процесс. При **любой** правке сервиса:

1. Правь копию в рабочей директории сессии.
2. **Бампни `SERVICE_VERSION`** и синхронно поменяй `..._EXPECTED_SERVICE_VERSION`
   в `fb2_reader_gui.py`. Совпадающая версия — единственный сигнал для GUI, что
   процесс можно не перезапускать; несовпадающая — что старый (зомби) процесс
   нужно убить и поднять заново.
   Из-за долгой истории правок номера вида `YYYY-MM-DD.N` не гарантированно
   уникальны между сессиями (нумерация локальная для каждого диалога) — если
   есть малейшее подозрение на коллизию с прошлой версией, добавляй понятный
   суффикс (`...-endofprompt-order-fix`), а не голое число.
3. `python3 -m py_compile <файл>.py` перед отправкой.
4. `SendUserFile` → `mcp__remote-devices__device_commit_files` на:
   - `J:\audiobook\<файл>.py` (эталонная копия в корне)
   - `J:\audiobook\CosyVoice3\<файл>.py` — **только для
     `cosyvoice3_rest_service.py`**, это реальная копия, которую запускает
     подпроцесс (GUI берёт её из `CosyVoice3/`, а не из корня).
   - `fb2_reader_gui.py`, если версия там тоже поменялась.
5. Попроси пользователя перезапустить сервис: закрыть GUI, затем
   `netstat -ano | findstr :5012` (или :5011) → `taskkill /F /PID <PID>` для
   каждого найденного процесса, и только потом запускать GUI заново.
   **Одного изменения версии недостаточно**, если сервис уже был поднят и
   GUI посчитал его версию подходящей — файл может лежать на диске уже
   исправленный, а в памяти процесса всё ещё крутится старый код. Это не
   гипотетический риск: за одну сессию отладки CosyVoice3 несколько раз
   ловили именно это (лог показывал совсем другие имена переменных, чем в
   доставленном файле — верный признак зомби-процесса).

## Отладка через remote-devices bridge

- `mcp__remote-devices__device_bash` — Linux-шелл, читает файлы пользователя
  через `$HOME/mnt/audiobook/...`. **Не может** исполнять `.exe` файлы из venv
  (`Exec format error` на Windows-бинарники) — для запуска Python-кода из
  венвов пользователя такой возможности нет вообще, только чтение/правка файлов
  и текстовые утилиты (`grep`, `sed`, `cat`, сам `python3` из Linux-моста для
  чтения/правки JSON и т.п., но не для импорта torch/venv-пакетов).
- Когда логика TTS-движка (CosyVoice3, любой другой) ведёт себя непонятно —
  **читай исходники движка прямо на диске пользователя** через `device_bash`
  вместо того чтобы гадать по документации/памяти. В этом проекте это
  неоднократно оказывалось единственным способом найти настоящую причину
  (например: `assert 151646 in text` внутри `cosyvoice/llm/llm.py`, который
  никакая публичная документация не упоминает).
- `fb2_reader_gui.log` **накапливается за весь день** и не ротируется по
  умолчанию — при разборе присланного лога всегда сверяй метки времени и ищи
  ПОСЛЕДНИЙ актуальный прогон (`grep -n "Загружаю модель\|Старт озвучки"`),
  а не первое совпадение с начала файла. Итоговые счётчики
  (`grep -c "200 OK"` / `grep -c "400"`) по всему файлу вводят в заблуждение,
  если файл содержит несколько прогонов подряд.
- Голосовые профили CosyVoice3 хранятся в
  `CosyVoice3/data/cosyvoice3_voices.json` (текст+путь к wav) и
  `CosyVoice3/data/voices/*.wav`. Загружаются в память **один раз при
  старте сервиса** — правка json на диске не подействует без перезапуска
  процесса (см. правило выше).

## Известные особенности CosyVoice3 (порт 5012)

Проверено через чтение исходников и официальный README
(`FunAudioLLM/Fun-CosyVoice3-0.5B` на HuggingFace) и подтверждённый на практике
community-issue (`FunAudioLLM/CosyVoice#1704`):

- Этот конкретный чекпоинт (`CosyVoice3LM`) **жёстко требует** токен
  `<|endofprompt|>` (id 151646) где-то в склеенных `prompt_text + text` —
  иначе `AssertionError` на каждом синтезе. Правильный формат по официальному
  примеру:
  `prompt_text = "You are a helpful assistant.<|endofprompt|>" + <реальный
  транскрипт образца>` — маркер СТОИТ МЕЖДУ вводной фразой и транскриптом,
  не после него и не вместо него (обе альтернативы уже пробовались и ломали
  либо стабильность, либо смысловое содержание синтеза).
- `MAX_PROMPT_SECONDS = 10.0` (образец обрезается до первых 10 сек) и
  `MAX_TRANSCRIBE_SECONDS` должны совпадать — иначе `/transcribe`
  распознаёт больше речи, чем реально попадёт в обрезанный образец, и текст
  перестаёт соответствовать аудио (искажённый/зацикленный синтез).
- `inference_zero_shot()` из `cosyvoice/cli/cosyvoice.py` сам заново режет
  переданный `tts_text` на предложения (`split=True`) — если текст уже
  порезан на фрагменты вызывающим кодом (как в этом проекте), нужно вызывать
  `frontend.text_normalize(..., split=False)` + `frontend.frontend_zero_shot()`
  + `model.tts()` напрямую, в обход публичного метода.
- Голос клонируется по акустике образца (`prompt_wav`), не по тексту
  `prompt_text` — но без соответствия текста и аудио модель всё равно даёт
  сбои/искажения, транскрипт должен быть точным.
- Для русского языка стоит ждать неточных ударений и лёгкой шероховатости
  звука по сравнению с ESpeech RL-V2 — это ограничение модели (wetext-фронтенд
  заточен под китайский/английский), не баг сервиса.

## Модуль ударений — АКТУАЛЬНО: один движок silero-stress + грамматический шлюз (8 октября 2026, вечер)

RUAccent, `ruaccent-predictor`, `stress_training.py` (подкоманды `build-dataset`/`train-predictor`) и `ruaccent_predictor_pkg/`
УДАЛЕНЫ из клиента и сервиса Silero полностью, без переключателей. (Остался только отдельный venv CosyVoice/XTTS в `install.bat`
со своим `ruaccent` — это другой сервис, к конвейеру Silero не относится.) Разделы ниже про Ollama/LM Studio/hybrid/predictor —
ИСТОРИЯ, код этих веток в программе больше не существует.

Конвейер (`apply_stress_layers(text, stress_engine, silero_accentor)` в `fb2_reader.py`):
1. словари `forced_stress_words.json` + `manual_stress_overrides.json` + файл правок книги (слова и фразы прячутся за плейсхолдерами
   `STRESSDICT<n>`; абсолютный приоритет) → 2. `numbers_to_words_ru` → 3. `apply_silero_layer`: silero-stress с левым контекстом
   (хвост предыдущего куска, `_silero_stress_primed`); слово берётся только если буквы совпали (с точностью до «+» и е/ё), «ё» принимается
   («все» → «вс+ё»), «лет» → «лёт» запрещено → 4. `_grammar_gate_pass` (slovnet; падеж/число: земли, сети, голоса…) →
   5. `global_prose_sanitizer` (таблица `_PROSE_WORDS` + `strip_particle_stress`) → 6. `strip_monosyllable_stress`.
- `stress_engine`: `"silero"` (по умолчанию) или `"none"`. Старые значения (`ruaccent`, `silero_stress`, `hybrid`, `ollama`, `lmstudio`)
  принимаются и означают `"silero"` (`normalize_stress_engine`); флага `--no-ruaccent` нет (`--stress-engine none`).
- Правило частиц: `strip_particle_stress` снимает случайное второе «+» в `-нибудь`, `-либо`, `-то`, `-таки`, `-ка` («когд+а-ниб+удь» → «когд+а-нибудь»).
- Правила фраз «в руки», «на караул», «пора бы», «знаком» (`_fix_znakom`), «больше» (`_fix_bolshe`) УДАЛЕНЫ — silero-stress решает их сам
  (тесты в разделе «neural cases»). Новые промахи добавлять в `_PROSE_WORDS` (только слова с одним чтением) или в `forced_stress_words.json`.
- REST-сервис (`silero_rest_service.py`) ничего не акцентирует: цифры → слова, `strip_mono`, синтез ровно того, что прислал клиент.
  `server_accent=false` → `save_wav(put_accent=False, put_yo=False)`; `true` → собственное угадывание Silero (когда silero-stress недоступен).
- Замер на главе 2 (4908 слов): silero-stress + шлюз 99.22% против 99.28% у прежней цепочки с предиктором, на CPU примерно в 170 раз быстрее.
- Отпечаток главы (`_params_fingerprint`) содержит `stress_dict_digest(словарь, текст главы)` — хэш ТОЛЬКО тех записей, чьи слова есть в главе:
  правка одной метки пересинтезирует ровно затронутые главы (раньше учитывалось лишь число записей).

## Вкладка «Словарь ударений» (редактор, `gui_stress_editor.py`)
`StressEditorMixin` подмешан в `AudiobookApp`; вкладка строится в `UIBuilderMixin._build_ui` (`_build_stress_editor_tab`).
- Слева: текст выбранной главы, поиск (регистр не важен, е = ё, необязательное «+» внутри слова, «слово целиком»), подсветка всех вхождений,
  ◀ ▶ / Enter — по вхождениям; двойной щелчок по слову грузит его в редактор; переключатель «исходный текст / с ударениями (предпросмотр)».
- Справа: слово рисуется по буквам, гласные кликабельны (`place_stress`: «+» встаёт перед гласной, переезжает, повторный щелчок снимает);
  «Добавить / обновить», «Удалить из словаря», список записей `forced_stress_words.json` с фильтром.
- Омографы: `fb2_reader.stress_word_variants` прогоняет КАЖДОЕ вхождение слова в главе через silero-stress → шлюз → санитайзер (без словаря)
  и группирует чтения; ≥2 разных чтения = красное предупреждение, строка таблицы подсвечивает места в тексте. Запись омографа в словарь
  требует подтверждения (она действует на все вхождения во всех книгах). Поток анализа не трогает Tk: результат кладётся в очередь,
  главный поток забирает её через `after` (`_se_post`/`_se_poll`).
- «Сохранить словарь» пишет файл сразу (`save_entries`: tmp + `os.replace`, комментарии-ключи с «_» сохраняются).
  «Предпросмотр» = `stress_dry_run` по главе. «Re-run Synthesis» = сохранить → `reload_stress_models()` (контекст, счётчики, кэши шлюза) →
  удалить `*.wav.meta.json` выбранных глав → `start_synthesis()`.
- Путь к файлу — `fb2_reader.DEFAULT_FORCED_STRESS_PATH` (`app_paths.user_file`): в собранном .exe это файл рядом с .exe.
- Чистая логика (без Tk) тестируется в `test_accentuation.py`; Tk-часть проверена вручную под Xvfb (`python3.12` + tkinter).

### LM Studio вместо Ollama (октябрь 2026)

У пользователя локальные модели крутятся в LM Studio (не только в Ollama), поэтому
`lmstudio` добавлен ровно туда же, где есть `ollama`: пятым провайдером в
`ATTRIBUTION_PROVIDERS` (атрибуция, умная эмоция, пол персонажей) и значением
`--stress-engine lmstudio` / пунктом движка ударений в GUI. Транспорт —
OpenAI-совместимый `POST {host}/v1/chat/completions` (`_lmstudio_chat_request`,
хост по умолчанию `LMSTUDIO_HOST_DEFAULT = http://localhost:1234`, сервер нужно
запустить на вкладке Developer -> Start Server); общая точка выбора
`_local_chat_request(..., backend="ollama"|"lmstudio")`. В поле «Модель» —
идентификатор загруженной модели как в LM Studio; `<think>...</think>` из ответа
вырезается. Поле адреса в GUI/`--ollama-host` общее для обоих (пусто = стандартный
порт выбранного бэкенда). Ключ не нужен.

### Скорость локальной LLM (октябрь 2026)

Ударения через `ollama`/`lmstudio` НЕ вызывают модель на каждый кусок: в начале
каждой главы `prewarm_ollama_stress` собирает все омографы главы и отправляет их
пачками по 25 (`_stress_collect`, `_stress_query_llm`); кусочки потом читают кэш
(`_stress_cache_get` — ключ вхождения = слово + по 12 символов контекста с каждой
стороны, у края куска сопоставление по неполному контексту). Все запросы к
локальным моделям ограничены по `max_tokens` (пропорционально числу элементов в
ответе) и отключают «рассуждение»: Ollama — `think: false` (с повтором без него,
если сервер не знает параметра), LM Studio — приписка `/no_think` и вырезание
`<think>`. Если всё равно медленно — основной подозреваемый нехватка VRAM: TTS
и LLM-модель (14B ≈ 9 ГБ) одновременно на одной 16-гиговой карте.

### Привязка голоса к персонажу (октябрь 2026)

Атрибуция говорящих (`resolve_voice_groups`) закрепляет голос за именем
персонажа в `dialogue_characters.json` (папка вывода). Новому персонажу
голос выбирает `_pick_voice_for_new_character`: пол персонажа определяет та же
LLM, что делала атрибуцию (`detect_character_genders`, один доп. запрос на
главу только для новых имён, читает фрагменты с упоминанием — понимает
прозвища и роли вроде «старуха»), при её сбое — разбор имени через
pymorphy3 (`_guess_name_gender`), пол голоса — по пометке "(муж.)/(жен.)" в
подписях Silero/Yandex/Qwen/Piper (`_voice_gender`); сначала берётся свободный
голос нужного пола, при неизвестном поле — старое круговое назначение.
Ручная правка — кнопка «Голоса персонажей…» в блоке диалогов GUI
(`_open_character_voices_dialog`), работает для всех режимов с набором голосов,
включая `qwen_tts`/`qwen_tts_local`.

### Ollama также как провайдер атрибуции говорящих и умной эмоции

С октября 2026 `ollama` — четвёртый пункт в `ATTRIBUTION_PROVIDERS` (наравне
с `yandexgpt`/`gemini`/`anthropic`), доступный и для атрибуции говорящих
(`attribute_speakers_llm`/`attribute_speakers_ollama`), и для умной эмоции
(`classify_paragraph_emotions_llm`/`classify_paragraph_emotions_ollama`) —
эти две фичи и так делят один и тот же диспетчер/провайдера, см. раздел
«Умная эмоция» выше. В отличие от остальных провайдеров, API-ключ не
нужен (поле можно оставить пустым — `_selected_attribution` в GUI это
учитывает отдельной веткой), но нужна заранее скачанная модель
(`ollama pull <модель>`) и запущенный `ollama serve`/приложение Ollama;
адрес сервера общий для атрибуции/эмоции и для `--stress-engine ollama`
(`ollama_host_var`/`--ollama-host`). При ошибке (Ollama не запущена,
модель не скачана, неожиданный ответ) — как и у остальных LLM-фич,
тихий откат на простое чередование голосов / единую эмоцию, не срывая
синтез главы.

### Надёжность ударений/интонаций и автозапуск локальной LLM (5 октября 2026)

- Ответы LLM по ударениям идут JSON-объектом по номерам; каждый пункт проверяется
  (`_stress_answer_ok`: то же слово, один "+" перед гласной или "ё"), невалидные/пропущенные
  перезапрашиваются меньшими пачками (`_stress_query_llm`). Раньше при "17 ответов вместо 18"
  вся пачка откатывалась на подсказки silero-stress. В промпте был неверный пример
  ("за+мок"); правильно "з+амок"/"зам+ок" — плюс ПЕРЕД ударной гласной.
- Ударение омографа ставится по КОНКРЕТНОМУ вхождению (`_ollama_stress_occurrence_forms` +
  параметр `occurrence_forms` у `apply_stress_dictionary_protected`), а не одно на все
  вхождения слова в куске. Все 29 записей `manual_stress_overrides.json` — омографы с одним
  фиксированным вариантом (голоса, места, лица, дома...); при движке lmstudio/ollama их
  перекрывает решение LLM по контексту, словарная запись — лишь запасной вариант.
- Умная эмоция: метки по номерам + перезапрос недостающих (раньше "14 вместо 15" сдвигало
  метки на соседние абзацы), сглаживание `smooth_emotion_prosody` (медианный фильтр, скользящее
  среднее, `SILERO_EMOTION_INTENSITY`=0.6) и просьба держать окраску сцены ровной.
- `ensure_local_llm` (вызывается из `_local_chat_request`): сам запускает `lms server start` /
  `ollama serve` и грузит модель (`lms load --context-length 8192 --ttl 900`; по TTL LM Studio
  выгружает модель и освобождает VRAM для TTS). Отключение: `AUDIOBOOK_LLM_AUTOSTART=0`.
  Проверено только на имитации `lms` — на реальном LM Studio ещё не запускалось.
- `forced_stress_words.json` ({"слово": "сл+ово"}) — слова, которые читаются ТОЛЬКО так: выше LLM,
  словаря и RUAccent (`_load_forced_stress`). Сейчас там "душу" -> "душ+у".
- Усиление "?"/"!" смягчено: `EMPHASIS_QUESTION_PITCH`/`EMPHASIS_EXCLAIM_PITCH`/`EMPHASIS_EXCLAIM_RATE`
  вместо пресетов pitch="high"/rate="fast" (от них интонация скакала на каждой реплике).
- Ударения омографов через LLM — ВЫБОР ИЗ ВАРИАНТОВ, а не генерация: `_stress_candidates(слово)`
  даёт все варианты ("з+амок", "зам+ок", плюс е->ё), `_ollama_stress_prompt` просит назвать НОМЕР
  варианта по контексту (подсказка silero-stress — как справка), `_stress_query_llm` берёт
  `cands[номер-1]`. Невозможны выдуманные слова/кривой "+"; пропущенные пункты перезапрашиваются.
  Цель — чтобы не приходилось вручную чинить слова по одному (forced_stress_words.json — лишь запасной выход).

## Рассмотренные и отложенные TTS-движки

- **OmniVoice** (open-source, 600+ языков, клонирование голоса + описание
  голоса текстом) — статья с русскоязычным бенчмарком:
  https://habr.com/ru/companies/raft/articles/1031560/ . Средняя оценка

  проблемы с ударениями омографов в русском. Автор статьи сам не
  рекомендует её для аудиокниг/подкастов (только короткие фразы, голосовые
  ассистенты, обучающие материалы) — то есть под задачу этого проекта
  (озвучка целых глав) не подходит по прямому назначению без доп.
  тестирования. Интеграцию не делали — если пользователь явно попросит
  попробовать, начать нужно с этой статьи и с проверки, есть ли у модели
  локальный REST/Gradio-интерфейс, аналогично Qwen3-TTS/CosyVoice.

- **SaluteSpeech / Сбер** (облачный TTS, был кратко полностью
  реализован в программе как режим `salute` 9 сентября 2026 — код и
  документация написаны, затем ПОЛНОСТЬЮ УДАЛЕНЫ в тот же день) —
  причина: страница подключения
  (developers.sber.ru/docs/ru/salutespeech/quick-start/integration-individuals)
  прямо говорит "С 15 июля 2026 года подключение для новых клиентов
  недоступно" — продажа пакетов и продление бесплатного Freemium-лимита
  остановлены, у кого уже был подключён сервис — тот донашивает
  оставшийся пакет, но новый ключ получить негде. Урок на будущее:
  ПЕРЕД тем как писать интеграцию нового облачного TTS (не только
  читать документацию по API), нужно сначала явно проверить страницу
  регистрации/подключения на предмет "недоступно для новых клиентов" —
  сама документация API при этом может выглядеть полностью актуальной
  и не иметь никаких предупреждений на странице обзора. Если пользователь
  явно попросит вернуть SaluteSpeech (например, если сервис снова
  откроется для новых клиентов, или у пользователя уже есть старый
  подключённый аккаунт) — реализация (OAuth, сертификат НУЦ Минцифры,
  синтез, GUI-блок) была рабочей и её можно быстро восстановить по
  этому же паттерну, что и `yandex`.

## Ручные ударения: ОДИН главный файл — `forced_stress_words.json`

Лежит рядом со скриптами/.exe (`J:\audiobook\forced_stress_words.json`), редактируется на вкладке «Словарь ударений» (или кнопкой «Открыть словарь ударений» в Блокноте).
В файле уже есть формы Клинкскейлс (`кл+инкскейлс`, -а, -у, -ом, -е, мн. ч.) и Сан-Мартин (`сан-март+ин`, -а, -у, -ом, -е; дефис в замене убирается — слово читается слитно).
Это единственный авторитетный источник ручных правок: слова из него читаются ТОЧНО так, как записано; нейросеть, silero-stress
и `global_prose_sanitizer` их не видят и не меняют (слово прячется за плейсхолдером на время всех слоёв).

```json
{
  "Нимиц": "Н+имиц",
  "замок": "зам+ок",
  "душу": "душ+у"
}
```

- Ключ — ОДНО слово без пробелов (регистр не важен, ищется целым словом). Значение — то же слово с `+` ПЕРЕД ударной гласной
  (`зам+ок` = замóк; `з+амок` = зáмок). Буква «ё» ударная сама — `+` можно не ставить, но можно (`вс+ё`).
- Форма слова одна: «замок» в словаре сработает во ВСЕХ предложениях, омографы по контексту словарём не различаются.
  Падежные формы (`Нимица`, `Нимицу`) пишутся отдельными строками.
- Приоритет сверху вниз: `forced_stress_words.json` > `<книга>.manual_stress_overrides.json` > `manual_stress_overrides.json`
  > silero-stress (+ «ё») > грамматический шлюз > `global_prose_sanitizer` (поверх слов НЕ из словаря).
- Ошибка в JSON (лишняя запятая, кавычки) = файл молча не читается, в консоли будет «Не удалось прочитать …». После правки перезапуск не нужен,
  файл читается при каждом запуске озвучки.

- GUI: «Открыть словарь ударений» открывает файл в Блокноте (`notepad.exe`, запасной вариант `os.startfile`) и пишет в журнал подсказку про
  сохранение/перезапуск главы. «Показать текст главы с ударениями» на вкладке «Проверка ударений» (`check_ambiguous_stress` -> `fb2_reader.stress_dry_run`; раньше кнопка «Проверить ударения» на «Озвучке») — сухой прогон ТОЙ ЖЕ цепочки,
  что идёт на озвучку (числа -> словарь -> silero-stress -> шлюз -> санитайзер), для выбранной главы (или первой), результат — окно
  с «+», подсвеченными жёлтым (копировать/сохранить). Старый отчёт по омографам (`check_ambiguous_stress.py`) из кнопки убран.
  Кнопка-дубликат «Словарь ударений» (диалог-редактор, писавший в manual_stress_overrides.json) и окно разбора омографов УДАЛЕНЫ:
  в интерфейсе одна кнопка словаря — «Открыть словарь ударений» (Блокнот, `forced_stress_words.json`).

## Числа

Цифры превращаются в слова ДО расстановки ударений (`numbers_to_words_ru` в `_accented_text_for_rest`), чтобы «десять» получило свой «+».
Слова всегда отделяются пробелами от соседних букв/цифр («10лет» → «десять лет», «20-летие» → «двадцать летие»), «5-6» — диапазон,
не «минус шесть». Страховка в `silero_rest_service.accentize_ssml_text_nodes`: цифры конвертируются ВСЕГДА, в том числе при
`server_accent=false` (раньше при `false` функция возвращала SSML без конвертации — сырые цифры уходили в Silero, и он их «глотал»).

## Заметки по сервису и тестам (7–8 октября 2026)

- SSML-`rate` ТОЛЬКО как «107%», НЕ «+7%» (Silero читает «+7%» как 7% скорости → предложение 27 с и ошибка «tensor a ... must match tensor b (5000)»).
- Хвостовой кусок короче 150 символов присоединяется к предыдущему (`_split_paragraphs_for_ssml`) — меньше отдельных вызовов синтеза = меньше скачков тембра.
- `test_accentuation.py` — запуск `python tools\test_accentuation.py` (нужны silero-stress; шлюз-тесты пропускаются без slovnet); известные промахи моделей помечены KNOWN-LIMITATION.

## Фразы в словаре ударений (8 октября 2026)

`forced_stress_words.json` (а также `manual_stress_overrides.json` и файл правок книги) теперь понимает ФРАЗЫ: ключ с пробелами.

```json
{
  "мы все": "мы вс+е",
  "вы все ещё": "вы вс+е ещё",
  "хонор харрингтон": "х+онор харр+ингтон"
}
```

- Значение — те же слова в том же количестве, с `+` перед ударной гласной; иначе фраза пропускается с сообщением в консоли.
- Поиск без учёта регистра, пробелы/переносы между словами любые, е и ё равны («вы все еще» = «вы все ещё»).
- Каждое слово фразы прячется за своим плейсхолдером (`_phrase_forms` -> `occurrence_forms`), поэтому нейросеть по-прежнему видит всё предложение как контекст.
- Более длинная фраза имеет приоритет над короткой; запись фразы приоритетнее одиночного слова.
- Тесты: раздел «phrase entries» в `test_accentuation.py`.

## Контекст для silero-stress: «прайминг» предыдущим куском (8 октября 2026)

- Проблема: silero-stress решает омографы по окну ~300 символов (`homosolver.window_size`), а конвейер отдаёт ему один кусок текста за раз —
  у первых слов куска нет левого контекста («Замок щёлкнул.», «Они все побежали…» → ошибка, хотя предыдущее предложение всё объясняет).
- Решение: `_silero_stress_primed` (в `apply_silero_layer`) подставляет перед текстом хвост ПРЕДЫДУЩЕГО куска (≈220 символов, без «+» и
  плейсхолдеров; хранится в `_stress_ctx_tail`, обновляется в конце `apply_stress_layers`) и оставляет в ответе только слова текущего куска.
  Любое несовпадение слов → обычный вызов без контекста. Счётчик: `_fallback_stats["ctx_primed"]`.
- `reset_stress_context()` вызывается в начале каждой главы (циклы озвучки) и в `stress_dry_run`; первый кусок главы идёт без контекста.
- Выключатель: переменная окружения `AUDIOBOOK_STRESS_CONTEXT=0`.
- Замер на свежем наборе из 12 пар «предыдущее предложение + целевое» (все/всё, замок, мука): без праймига 6/12, с ним 11/12.
- Не сделано: файл контекстных регулярных правил для `homosolver.load_regex_dict` (возможное продолжение; `Мы все побежали.` без контекста по-прежнему ошибка).
- Тесты: раздел «context priming» в `test_accentuation.py` (`run_chain` теперь сбрасывает контекст между независимыми случаями).

## Grammar gate (case/number stress homographs)
`grammar_gate.py` (models: `fb2_reader fetch-models`), hooked in `apply_stress_layers` (`_grammar_gate_pass`, right
before `global_prose_sanitizer`). slovnet (Natasha) tags every sentence (POS/Case/Number, CPU, ~25 ms); a
paradigm table (F: sg ending-stressed/pl stem-stressed, M: opposite, S: never moves — see the lists at
the top of the module) maps the tag to the stress of the homograph surface form. Number is cross-checked
with the modifier on the left (adjectives, determiners, numerals, participles). Only NOUN/PROPN tokens are
touched. Off with AUDIOBOOK_GRAMMAR_GATE=0; silently off when slovnet/navec/razdel or ./grammar_gate_models are
missing (install.bat installs both). To teach it a word, add its stem-stressed form to _F_WORDS/_M_WORDS/_S_WORDS.
«все/всё»: книга пишет оба слова «все»; шлюз (`_vse_form`) решает по числу из slovnet (plural → «все», neuter sing → «вс+ё»; «все, кто» — всегда «все»),
тегирует нейтральное написание «все» (ё от прежнего слоя игнорируется). Проверено на гл. 3 и 4 (48 вхождений) без словарных фраз; тесты в разделе «grammar gate».
Known tagger weakness: a quoted noun after a differently-numbered word («пэрам «земли»») can get the wrong number.

## One program, one orchestrator (monolith, 8 Oct 2026)
There are NO separate workflow scripts or folders any more. `fb2_reader.py` is the entry point AND the orchestrator
(`run_subcommand`, called from `main()`): no arguments = GUI; `book.fb2 --mode ...` = synthesis;
`fb2_reader <fetch-models|selftest|serve-silero|gui> ...` = every other phase
(`download_grammar_models.py` is gone; `finetune/` was deleted and must not be recreated).
* `app_paths.py` is the ONLY place that knows where files are: from source everything is next to the .py files;
  frozen (PyInstaller) read-only assets come from `sys._MEIPASS`, user-editable/writable files live next to the exe
  (`seed_defaults()` copies the packed dictionaries there on first start) and a copy next to the exe always wins over
  the packed one. Never build paths from `__file__` / `Path.cwd()` — use `resolve_asset()` / `user_file()`.
* `serve-silero` runs the Silero REST service in the same exe (the GUI spawns `[sys.executable, "serve-silero"]` when
  frozen). CosyVoice/Qwen servers are still external.
* Build: `install.bat` does everything (venv, dependencies, `fb2_reader.py fetch-models`, then a forced clean build with
  `set "AUDIOBOOK_ONEFILE=1"` + `python -m PyInstaller main.spec --noconfirm --clean` -> `fb2_reader.exe`, strictly ONE file).
  `AUDIOBOOK_ONEFILE=0` gives a one-folder debug build. Not bundled: silero_model_v5_5_ru.pt, pretrained_models/, ffmpeg,
  piper voices, CosyVoice. Env overrides: AUDIOBOOK_GRAMMAR_DIR, AUDIOBOOK_GRAMMAR_GATE=0.
* `main.spec` packs silero-stress, slovnet/navec/razdel, `grammar_gate_models/`, the seed dictionaries and `gui_stress_editor`;
  it excludes ruaccent/transformers/tokenizers. All editable files (incl. the dictionary editor's `forced_stress_words.json`) are
  resolved through `app_paths.user_file` — next to the exe, never inside `_MEIPASS`.
* `fb2_reader.py` registers itself as `sys.modules["fb2_reader"]` when run as `__main__` (no double import).

## Вопросы пользователю по ударению (`stress_questions.py`, 10 октября 2026)
Идея: если модель не знает слово — спросить, а не гадать. Измерено, что автоматические «вторые мнения» хуже модели: независимый корпус расходится с цепочкой на ~95 типах слов глав 1–50,
правы цепочка в 91 и корпус в 4 (корпус хранит одно чтение омографов и ошибается на формах вроде «поднял»), поэтому слой «корпус перебивает модель» НЕ внедрён. Совпадение разных чтений одного слова
по книге тоже чаще законный омограф. Поэтому: `stress_questions.py scan книга.fb2 ПАПКА [--top N]` — прогон цепочки, затем вопросы трёх видов (name: заглавное слово вне корпуса; unknown: слово вне корпуса
и вне словаря pymorphy3; inconsistent: разные метки у одного слова). Имена группируются по лемме. Страница `ПАПКА/index.html`: аудио каждого варианта голосом xenia, радиокнопки, «Экспорт» → decisions.json;
`apply decisions.json` пишет в `forced_stress_words.json` (+ журнал), ответ распространяется на падежные формы, у которых ударная гласная лежит в общей основе. Слова из словаря не спрашиваются повторно.
На «Пепле победы»: 361 вопрос (276 имён, 49 слов, 36 нестабильных), на страницу идёт топ-60 по частоте. Слух решает пользователь; отдельной вкладки в GUI пока нет.

### Дообучение silero-stress: пилот (10 октября 2026) — вывод: пока не стоит
- Устройство: `accentor.pt` — torch.package с исходниками. Пословная модель (`accentor.model`, TorchScript, 2,06 М параметров, n-граммный embedding + MLP, вход — слово, выход — номер ударной гласной, 0-based) без контекста; омографы решает отдельный `homosolver` (BERT-подобный, 29 М). Обучаемы оба; дообучение технически возможно (`ft_experiment/ft_pilot.py`).
- УТОЧНЕНИЕ прежнего утверждения «нет оценки уверенности»: она есть (`accentor._get_model_preds` → softmax), но слабая: из 157 слов словаря, где модель ошиблась, p<0,99 только у 46 (29%), p<0,9 у 21; при этом порог 0,99 помечает 7% обычных слов. Ошибки в основном уверенные.
- Пилот: 145 слов словаря (ответы ассистента, НЕ прослушанные) + 4000 слов «воспроизведения» ответов старой модели против забывания; тест — 80 слов с другими основами. Точность на тесте 38,8% → 43,8–46,3% (n=80, разница в пределах шума), трейн запоминается (88%), но 2,2% обычных слов меняют ответ, а согласие с корпусом падает 96,5% → 95,7–96,3%. То есть при таком объёме данных дообучение — это запоминание (его надёжнее делает словарь) плюс небольшой регресс.
- Условие, при котором стоит повторить: несколько сотен ПРОСЛУШАННЫХ ответов (их собирает `stress_questions.py`), отложенная выборка ≥200 слов, критерий — рост на отложенной выборке без падения согласия с корпусом и без дрейфа. Полученные веса клали бы отдельным файлом с проверкой SHA-256 в `stress_versions.lock.json`, не правкой пакета.
- Бывшая вкладка «Вопросы по ударению» теперь часть вкладки «Проверка ударений» (см. раздел выше); логика `stress_questions.scan_chapters` без изменений.

## Защита текста, ASR-вычитка и интервалы (14 октября 2026; идеи из серии статей servinosm на Хабре про TTS/ASR)
- **`_text_guard`** (`fb2_reader.py`, вокруг каждого слоя `apply_stress_layers`): слой не может менять буквы (допустимы только «+» и е/ё). Нарушил — для этого куска слой пропускается
  (теряются только метки, не слова), счётчик `_fallback_stats["text_guard"]`, первые 20 случаев в консоль. Отключить нельзя и не нужно. Тест — «text guard» в `test_accentuation.py`.
  Сервис Silero не менялся, `SERVICE_VERSION` не бампали. Реальный прогон цепочки на Windows после правки НЕ запускался: после первого прогона смотреть, не растёт ли `text_guard` (должно быть 0).
- **`tools/audio_verify.py`**: к покрытию добавлены WER, CER (по выравниванию слов + точное расстояние Левенштейна в расходящихся группах), `loop_ratio` (zlib по окнам из 60 слов ASR) и флаг `resynth`
  (CER > 0,05, или пропущенный кусок ≥ 6 слов, или loop_ratio > 3,0). Порог петли: обычный текст книги даёт до ~2,4, зацикленная фраза ~10 (замерено на `pepel-pobedy.fb2`, а не на реальном ASR — откалибровать на первом прогоне).
  Различия CER меньше ~0,01 — шум самой ASR. ASR НЕ проверяет ударение, только то, что текст произнесён.
- **`stress_benchmark.py`**: к итогу добавлен 95% интервал Уилсона и вывод «различимы / не различимы». На золоте из 68 целей 64/68 (94,1%) и 67/68 (98,5%) имеют ПЕРЕКРЫВАЮЩИЕСЯ интервалы (85,8–97,7 и 92,1–99,7):
  прирост цепочки над сырым silero-stress на этом наборе статистически не доказан. Чтобы доказать, нужно золото ≥ 200 целей.
